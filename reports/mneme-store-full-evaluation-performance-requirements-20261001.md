# Mneme 长历史增量存储性能需求

日期：2026-10-01  
来源：Agent Memory Leaderboard 文本赛道 Full 评测  
涉及版本：mnemekit 0.4.0、mneme-api 0.1.5–0.1.7

## 1. 结论

Mneme 0.4.0 的检索质量接口已经满足比赛接入需求，但当前 `Store` 的加载与持久化方式无法承载 Full 规模的长历史持续写入。

问题集中在存储生命周期，不涉及 Evidence projection、排序或记忆算法语义：

1. `Memory` 初始化时读取用户的全部 turn JSON，并重建内存索引。
2. 新增 turn 后重写完整的 `inverted.json`。
3. 新增事件后重写完整的 `events.json`。
4. 写入成本随用户历史增长，长期运行呈明显的超线性增长。
5. 为避免重复加载而长期缓存 `Memory` 时，每个活跃用户又会占用较多内存。

API 侧缓存只能在内存与吞吐之间折中，不能消除核心 Store 的全量加载和全量写回成本。核心库需要支持增量加载与增量持久化。

## 2. Full 实测现象

本次 Full 包含 42,161 个 Add 单元，平台配置上限为 Add 16、Search 16。单个 Add 最多包含 20 条消息，平台允许单请求最长运行 30 分钟。

### 2.1 原始 API 行为

原 API 每个请求重新创建 `Memory`，以保证进程间一致性和崩溃恢复。Full 首次运行约 8.75 小时后：

- 完成 894 / 42,161，进度 2.1%。
- 平均约 102 个 Add 单元/小时。
- 服务最终连 Health 请求也无法响应。
- Full 因 Search ReadTimeout 失败，可从检查点续跑。

代码检查确认，每次创建 `Memory` 都会触发 Store 对该用户历史的完整加载。该行为是主要吞吐瓶颈。

### 2.2 API 缓存实验

mneme-api 0.1.6 增加按用户缓存的 `Memory`，不改变 Mneme 调用、写入内容或 Search 结果。

在同一用户连续 38 个 Add 的本地回放中：

| 配置 | 总耗时 | 最后一个 Add |
|---|---:|---:|
| 每次重新加载 | 66.35 秒 | 3.10 秒 |
| 复用 Memory | 9.90 秒 | 0.84 秒 |

缓存带来约 6.7 倍加速，证明重复加载是主要成本之一。

### 2.3 内存限制

部署机有约 2 GB 内存且没有 Swap。缓存 16 个用户并恢复 Full 后：

- API RSS 从约 228 MB 增长到接近 1 GB。
- 系统可用内存降到约 620 MB。
- 随后公网 Health 与 SSH 同时失去响应。

将 API 内部并发和缓存用户数都降至 4 后，服务恢复稳定，但平台在约 16 个活跃用户间轮转时会频繁淘汰缓存，重新触发完整历史加载。稳定性提高，吞吐明显下降。

### 2.4 中断恢复成本

服务器失去响应时留下 15 个未完成请求。服务恢复后，每个相关用户都需要通过 journal 完整重放历史并生成新 generation。部分 Add 因此耗时约 4.5 分钟。

这套恢复方式保证了正确性，但恢复成本同样随完整历史增长。

## 3. API 层已经完成的改进

以下问题已由 mneme-api 处理，不要求 Mneme 核心重复实现：

- 按 `user_id` 严格隔离目录。
- 同一用户使用跨进程文件锁串行操作。
- `request_id` 幂等和 payload 冲突检查。
- SQLite journal 记录请求状态。
- 中断后构建新 generation，成功后原子切换。
- 单进程 LRU 缓存活跃用户的 `Memory`。
- 使用 generation 与已完成请求数检查缓存新鲜度。
- 限制 API 内部并发，避免小内存机器失去响应。
- Health 不占用同步业务线程池。

这些措施不能解决 Store 内部的全量读写复杂度。

## 4. 核心需求

### P0：增量恢复 Store

创建 `Memory(root=...)` 时，不应为恢复可检索状态而逐个打开并解析全部历史 turn JSON。

至少需要一种持久化索引快照或等价机制，使启动成本主要取决于索引大小和新增日志，而不是历史文件数量乘以单文件打开成本。

目标：同一用户已有 2,000 个 turn 时，重新打开 Store 的耗时不超过 2 秒；已有 10,000 个 turn 时不超过 5 秒。验收机器和磁盘规格需要随基准结果记录。

### P0：增量更新倒排索引

新增一个 turn 时，不应重写完整的 `inverted.json`。应只写入本次新增或变更的 posting，或者采用可追加日志加定期压缩的结构。

目标：在历史从 1,000 增长到 10,000 个 turn 的过程中，单 turn 持久化耗时的 P95 增长不超过 2 倍。

### P0：增量更新事件数据

新增或扩展事件时，不应在每条消息后重写完整的 `events.json`。事件应支持按 ID 独立更新、追加日志或数据库事务。

目标：事件数量增长时，更新一个事件的写入量不与全部事件文件大小线性相关。

### P0：批量记忆接口

比赛一次 Add 最多包含 20 条有序消息。核心库需要公开批量写入接口，使一次 Add 可以：

- 只打开一次事务或写入批次。
- 按现有顺序形成相同的 turn、event、fact 和 atom。
- 批次末尾统一刷新索引。
- 成功返回后立即可被 `search_evidence()` 检索。

建议接口形态由核心库决定，但必须避免 API 循环调用 `remember()` 时每条消息都触发一次完整索引写回。

### P1：有界内存的活跃 Store

一个打开的 `Memory` 不应要求将全部历史 turn 文本和全部派生对象常驻内存。至少应支持按需读取正文，并只常驻检索所需的紧凑索引。

目标：10,000 个中等长度 turn 的打开 Store，其稳定 RSS 增量应有明确基准，并支持在 4 GB 服务上同时保留至少 16 个典型评测用户。

### P1：低成本故障恢复

需要提供能够验证已提交边界的持久化机制，使 API 不必通过重新调用全部历史 `remember()` 来恢复一个中断请求。

可接受的实现包括事务、write-ahead log、commit marker 或核心库自己的 generation，但恢复后必须满足下述语义约束。

## 5. 必须保持的语义

性能改造不得改变以下行为：

- `Memory.search_evidence(query, topn=100)` 的 EvidenceItem、EvidenceSpan 内容与顺序。
- 默认 projection 及 Top-K 在 projection 后执行的规则。
- 每个 span 的 `source_id`、`role`、`timestamp` 和 `text`。
- session/event 的组织关系。
- 相同写入顺序下的检索结果可复现性。
- Add 成功返回后，后续 Search 立即可见。
- 崩溃只允许出现“整个批次已提交”或“整个批次未提交”，不得暴露部分批次。
- 现有 0.4.0 数据至少可只读打开；若需要迁移，应提供显式迁移工具，不做静默语义转换。

## 6. 建议基准

核心库应增加独立于比赛平台的长历史基准，至少覆盖：

1. 单用户顺序写入 100、1,000、5,000、10,000 个 turn。
2. 每个检查点重新创建 `Memory`，记录加载时间和 RSS。
3. 记录单 turn 写入的 P50、P95、P99。
4. 记录 20 条消息批量写入的延迟。
5. 记录索引与事件文件的实际写入字节数。
6. 在写入中途模拟进程退出，记录恢复时间并验证结果无重复、无缺失。
7. 同一数据分别比较增量前后的 `search()`、`recall()` 和 `search_evidence()` 输出。

基准输入可以使用合成文本，不需要使用或公开 AML 评测数据。

## 7. 验收门槛

第一阶段以能够稳定完成 AML Full 为目标：

- Add 16 的外部请求压力下，服务保持 Health 可用。
- 4 GB 内存环境中，进程峰值 RSS 不超过 3 GB。
- 10,000 turn 用户的单次 Add P95 小于 10 秒。
- 任意单请求不接近平台 30 分钟超时。
- 42,161 个 Add 单元预计在 36 小时内完成。
- 发生进程重启后，可在 5 分钟内恢复服务并继续请求。
- 与 0.4.0 固定样本的 Evidence 输出保持一致。

最终目标应达到平台通常 0.5–2 天完成 Full 的容量预期，而不是依赖长达数周的运行窗口。

## 8. 推荐实施顺序

1. 将 `inverted.json` 和 `events.json` 从全量重写改为增量持久化。
2. 增加批量 remember，使一次 Add 只刷新一次持久化状态。
3. 增加可直接加载的索引快照，消除逐 turn 文件扫描。
4. 降低打开 Store 的常驻内存，支持更多活跃用户。
5. 将事务或 WAL 下沉到核心库，缩短中断恢复路径。

前三项完成后即可重新跑离线容量回放；在容量门槛通过前，不建议再次消耗新的 Full 名额。
