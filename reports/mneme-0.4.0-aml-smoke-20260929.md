# Mneme 0.4.0 Agent Memory Leaderboard Smoke 报告

## 结论

Mneme 0.4.0 的新默认 evidence projection `TAG_GRAPH_DEDUP` 已通过 Agent Memory Leaderboard 文本赛道 Smoke。Add、Search、统一 Answer 和 Eval 四个阶段全部成功，说明 `Memory.search_evidence()` 返回的 EvidenceItem、多 span 内容和排序可以被平台完整消费。

本次 Smoke 综合分为 **49.75**，上一版 Mneme 0.3.1 的同类 Smoke 为 **51.17**，下降 **1.42** 分。分项变化并不一致：G 上下文学习与执行提高 25 分，Streaming 提高 4.17 分；A 显式事实召回下降 20 分，C 时间与事件序列下降 10 分；其余维度持平。

Smoke 只有 46 个样本，各非 Streaming 分项只有 2–6 个样本。随后完成的一次完全不变复跑确认：A 下降和 G 提升可以复现，C 下降没有复现，Streaming 两次均高于 0.3.1，但存在波动。

## API 接入

API 继续直接调用核心公开接口：

```python
items = memory.search_evidence(query, topn=top_k)
```

调用没有显式传入 projection，因此使用 Mneme 0.4.0 的默认值 `TAG_GRAPH_DEDUP`。API 层没有实现额外召回、排序、图扩展、投影、去重或 span 截断。

每个 EvidenceItem 被转换为一条 AML Search 结果；每个 span 的 `source_id`、`role`、`timestamp` 和 `text` 被保留在 `content` 中。平台成功完成 Search、Answer 和 Eval，证明这一返回形式符合当前 AML 契约。

## 对核心方案的观察

1. **新默认方案通过了真实端到端接口验证。** `TAG_GRAPH_DEDUP` 没有造成 Search 契约、Answer 输入或 Eval 阶段失败，可以作为正式比赛接口的可用投影方案。

2. **执行类问题出现正向信号。** G4 从 0 提高至 50，是本次最大正向变化；Streaming Online 也有所提高。这与图扩展和去重可能带来的跨片段组织能力一致，但目前不能从 4 个 G 样本中确认因果。

3. **直接事实和时间证据出现负向信号。** A1、A2、C1 和 C2 同时下降。需要检查图扩展与去重后，直接命中的 span 是否仍位于 EvidenceItem 前部，以及事实更新中的旧值、新值和时间信息是否被正确排序。

4. **多跳分数没有变化。** B 总分仍为 33.33，B2 仍为 0。新图投影在本轮 Smoke 中没有表现出多跳收益，但该维度只有 3 个样本，不能据此否定方案。

5. **治理能力没有改善。** D 仍为 20，D1 仍为 0。事实覆盖、撤销、冲突和当前有效状态仍应作为核心侧的主要检查方向。

6. **Reader token 风险仍然存在。** AML 正式评测按 Search 顺序将候选放入 Reader 输入，超出预算后不再使用后排内容。虽然 `TAG_GRAPH_DEDUP` 会去重，仍需测量单个 EvidenceItem 的 span 数、token 数和关键信息位置。

## 性能观察

Mneme 0.3.1 Smoke 用时 14 分 22 秒，0.4.0 用时 40 分 15 秒，0.4.0 总耗时约为上一轮的 **2.8 倍**。

运行过程中最明显的长尾出现在 Add 阶段：前半段稳定推进，后几个长历史样本耗时逐步增加。Search 阶段也出现少量长尾，但最终没有超时。平台允许单个 Add/Search 请求最长运行 30 分钟，本轮没有触发该限制。

这不是严格的核心性能基准：两次任务的部署负载和平台调度可能不同。不过差异足够大，建议在 Full 前用同一批 Add 请求做本地计时，记录每次请求的消息数、已有历史规模和处理耗时，判断是否存在随用户历史增长的非线性开销。

## 建议的下一步

1. 保持 0.4.0 生产方案不变，优先增加 Search evidence 预算诊断，不继续盲改核心。
2. 对 A/C 相关的事实与时间样例检查 EvidenceItem 内的 span 排序，确认直接证据是否被图扩展内容挤到后部。
3. 对 D 类构造事实更新、冲突、撤销和当前状态样例，检查旧事实是否仍被同等呈现。
4. 用现有 Add journal 做离线性能复放，重点测量长历史用户后期 Add 和 Search 的耗时增长。
5. 在 Full 前统计 Search 返回的 item 数、span 数和 token 总量，并记录被 Reader 截断的风险比例。

## 限制

- Smoke 不公开具体问题、金标答案、单题检索证据或失败原因，无法把分数变化归因到某个具体核心机制。
- 非 Streaming 分项样本很少，单个样本即可造成 10–50 分变化。
- 两轮任务不是并行运行，耗时差异可能包含部署负载和平台调度影响。
- 本次没有运行 Full，Full 额度仍为 0/2。
